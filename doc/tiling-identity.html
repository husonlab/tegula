Tegula · identity scheme

Delaney–Dress Keys

How to give every tiling a permanent identifier, a citable catalog number, and a name a person can read — and why the numbers we have today are none of those things.

Daniel H. Huson 18 August 2026 Draft 1 · for discussion

Tegula ships five databases holding several million periodic tilings, each encoded as a Delaney–Dress symbol. Every tiling in them has a number. That number is the only handle we currently have for saying this tiling — in a paper, in a saved file, in a URL, in conversation.

It does not survive. This document shows why, and proposes a replacement built from three separate things that we have so far been asking one number to do at once.

1 The number is not a property of the tiling

The id column of a .tdb file records the order in which the enumeration happened to emit each symbol. Two databases can hold precisely the same tilings and number them completely differently. Ours do.

The same tiling in three of our databases
DatabaseTilingsSymbol <…:7:1 3 5 7,2 3 4 6 7,1 4 5 7:3 4,9 4>
tilings-1-16795,590id 1000
tilings-1-195,214,516id 1000
tilings-1-185,214,516id 937

tilings-1-18 and tilings-1-19 hold identical content — same 5,214,516 symbols, same distribution across sizes 1 to 18 — under two different numberings. Restricting both to symbols of size ≤ 14 and lining them up tiling by tiling, 141,748 of 141,785 have different ids in the two files. And euclidean-1-24 and spherical-1-24 each restart from 1, so four independent numbering spaces are already in circulation, all of whose members are called things like “tiling 1000”.

This leaks into saved files

The number is written into the serialized symbol as its leading field — <1000.0:7:…>. A .tgs file therefore carries a number whose meaning depends on which database the reader happens to have. It looks like an identifier and behaves like a build artifact.

2 Three jobs, three layers

Identity, citation and readability have different requirements, and no single string satisfies all of them. Splitting them makes each one easy.

The load-bearing rule is that the key is the identity. A catalog number is only meaningful once you say which catalog; a nickname is never authoritative. Everything that must survive — file formats, URLs, cross-references between papers — hangs off the key.

3 The canonical form

Two Delaney–Dress symbols describe the same tiling exactly when they are isomorphic, that is, when one can be relabeled into the other. A canonical form picks one representative of each isomorphism class, so that isomorphic symbols become literally the same string.

Specification

For a connected symbol of size n, take each flag in turn as a starting point and build a relabeling:

  1. Give the starting flag the new label 1, and put its s0-, s1- and s2-images into three queues, one per index.
  2. Repeatedly draw from the lowest-numbered non-empty queue — from the back for indices 0 and 1, from the front for index 2 — discarding flags that already have a label. Give the first unlabeled flag drawn the next new label, and put its images under the other two indices into their queues. Stop when every flag has a label.
  3. Write down the protocol of that relabeling: the 5n numbers s0(1)…s0(n), s1(1)…s1(n), s2(1)…s2(n), m01(1)…m01(n), m12(1)…m12(n). Together with m02, which is always 2, that is the whole symbol, so a protocol can be read back.

The canonical form is the relabeling whose protocol is smallest as a sequence of numbers. If the symbol is not connected, canonicalize each component this way and concatenate the components in increasing order of protocol.

Why those two choices

The queue discipline is Olaf Delgado-Friedrichs', used in Gavrog, and his reason for it is readability: drawing indices 0 and 1 from the back exhausts a tile before moving on, so the flags of a tile come out consecutively numbered. Across 5,000 symbols drawn from the databases this holds for every tile; the obvious breadth-first alternative manages it for 46%. For a catalog people are going to read, that is worth having.

Comparing protocols rather than written symbols matters more than it looks. A rule that compares the text of a symbol makes the canonical form depend on how symbols are printed — spacing, separators, digit widths — so a later change to the output format would silently change every identifier in the catalog. A sequence of numbers has no such coupling. It is also what makes the computation cheap, since candidates can be compared without ever being rendered.

The shape of the algorithm is Algorithm 8 of Delgado-Friedrichs (2003) — try every seed, relabel, keep the smallest — which deliberately leaves the comparison open: "The particular choice of comparison function is irrelevant here as long as it is used consistently." Asked whether his own implementation should be treated as the standard, he replied that the queue discipline is a readability choice he has not applied consistently, and that we should use whatever works best for us. The protocol above is that choice, made once and fixed here.

<0.0:7:1 3 5 7,2 3 4 6 7,1 4 5 7:3 4,9 4>
  • Symbol number, forced to 0.0 — it is not part of the tiling
  • The three involutions s0, s1, s2 on the flags
  • Size, and the m01 / m12 values per orbit

4 The canonical key

The canonical form is the true identity, but it runs to a hundred-odd characters and cannot be read aloud. The key is a short stand-in: the size of the symbol, then the leading bits of the SHA-256 hash of the protocol, written in Crockford base 32 and grouped in fours.

DS07-80VG-B42W-4N1Y
  • Size of the Delaney–Dress symbol
  • 60 bits of SHA-256 of the protocol, Crockford base 32 (no I, L, O or U, so it cannot be misread)

Putting the size in front partitions the hash space: only symbols of the same size can ever collide, and the biggest size class we have published holds 3,404,473 tilings. That makes 60 bits very comfortable now, and leaves an obvious upgrade path.

Because a published catalog is complete and frozen, this is not left to probability. Collisions can be checked exhaustively once, at publication time, and certified. The tool does that check on every run; across all five databases it reports zero at 60 bits.

Recommendation

Publish the current catalogs at 60 bits. If the 2.4 billion tilings are ever released, use 80 bits for that catalog and say so in its header — the size prefix means the two schemes cannot be confused for one another.

A self-contained alternative

A hash is a one-way handle: it identifies a tiling but cannot produce it, so resolving one needs a catalog. A canonical form can instead be written directly, packed into the same alphabet, and the result is a name that is the tiling. DSymbolCode does that, and the format is specified in full in its documentation.

DS18-9ANA-NANA-M040-0ANA-K14
  • Size of the symbol, for people; it is in the bits as well
  • The canonical form itself, bit-packed, in the same Crockford base 32

The packing spends one bit where the next flag pairs with the one after it, and short codes on the m values 3 and 4. Both are cheap because of the traversal in section 3: numbering a tile's flags consecutively is exactly what makes s_i(a) almost always the next unpaired flag. 83% of the pair-ranks come out 0 or 1, and 62% of m values are 3 or 4. The readability choice and the compression turn out to be the same choice.

Roughly ten characters more at the sizes that fill the catalog, in exchange for needing no registry to resolve a name, no collision analysis at all — it is a bijection, so section 4's bit budget simply does not arise — and the ability to name a tiling nobody has enumerated. That last case is not hypothetical: a reader who reshapes a tiling in Tegula has something no catalog contains, and a hash of it resolves to nothing.

Reading a code is deliberately forgiving of transcription: case is ignored, hyphens are optional, I and L read as 1 and O as 0, and the prefix may be left off. Decoding also re-encodes and compares, so a code that has been damaged is refused rather than silently yielding a different tiling. That catches 90.3% of single-character corruptions; the remaining 9.7% land on another valid tiling of the same size, which one extra check character would reduce roughly thirty-fold if codes are ever meant to be typed by hand rather than scanned or pasted.

Every character of a code is in the QR alphanumeric set, which packs 5.5 bits per character, so a code of any size we hold fits in a 25 × 25 module QR code at medium error correction — small enough to sit in the corner of a rendered tiling. Scanning one reconstructs the tiling offline, with no server and no catalog, which is only true because the name is reversible.

5 The catalog number

Mathematicians want to write “tiling 937”, not a hash. A number is fine — the mistake was deriving it from the enumeration order instead of from the tilings themselves.

Ordering rule

Sort by size, and within one size by protocol as a sequence of numbers. Number the result 1, 2, 3, …

This has two consequences that the current numbering lacks. Anyone holding the same set of symbols recomputes the same numbers, without needing our software or our enumeration order. And because size is the primary key, extending the catalog to larger symbols appends to it: every number already published keeps its meaning.

Note that the ordering depends only on the canonical form, not on the hash. Key width and even the hash function stay free parameters that can be changed later without renumbering anything.

Pin down the universe first

A catalog number means nothing until the set it indexes is fixed. The same tiling sits at #1 in euclidean-1-24 and #4 in tilings-1-19 — both correct, because they are different catalogs. The key is identical in both, which is exactly the division of labour we want.

So the catalog must state, and then never change: the dimension (2), the range of sizes, which geometries, and whether anything is filtered out. Our current files variously split by geometry and carry normal, maximal and colorable flags. All 3-dimensional Delaney–Dress symbols of size ≤ N, unfiltered is the only scope that will not need revision — filter in queries, not in the catalog.

Publishing

  • Deposit for a DOI. Zenodo handles these sizes easily; the compressed catalogs run from 18 to 125 MB.
  • Include a plain-text listing of canonical forms, one per line, alongside the SQLite files. That is what makes the catalog definitive rather than Tegula's — anyone can regenerate the numbering from it with no dependency on our code.
  • Include the canonicalization specification (section 3) as prose, plus the reference implementation.
  • Make the keys resolvable. tegula.org/t/DS07-80VG-B42W-4N1Y returning a page with a picture is what makes an identifier feel real. A number nobody can click stays theoretical.

6 A name a person can read

Everything needed for a descriptive name is already computed and stored: orbifold symbol, geometry, transitivity counts, tile and vertex figures. A name is just a fixed way of reading those out.

<geometry> <orbifold> <tiles>/<edges>/<vertices> [<tile degrees>]

euclidean  *632  1/1/1  [3]        the triangular tiling
euclidean  *632  1/1/1  [6]        the hexagonal tiling
euclidean  *333  3/3/3  [3,3,12]
hyperbolic 2*32  2/3/2  [3,4]

A specialist reads that and knows what the tiling is without looking anything up, which is the whole point — it needs no registry and no lookup table, because it is regenerated from the symbol every time.

Nicknames, kept strictly separate

For the couple of hundred tilings that already have human names, ship a small table keyed by canonical key and fall back to the descriptive name for everything else:

This is also where the catalog connects to the existing literature instead of competing with it: the Grünbaum–Shephard isohedral types IH1–IH93, the Laves nets, the uniform tilings, the named nets in RCSR and EPINET. A community-extensible JSON file keyed by canonical key costs nothing and buys interoperability.

The same slot absorbs AI-suggested names. A user who reshapes and recolours a tiling has not changed its Delaney–Dress symbol, so its key and descriptive name are untouched; what they have made is a rendering, and giving that rendering an evocative name is a nickname operation. Useful, and firmly outside the identity system.

8 Implementation

Two pieces, both in the Tegula source tree.

tegula.core.dsymbols.DSymbolAlgorithms

canonicalForm(ds)        → DSymbol   the canonical representative
canonicalString(ds)      → String    that form, as a valid D-symbol string
canonicalProtocol(ds)    → int[]     its protocol, the normative object
canonicalKey(ds)         → String    "DS07-80VG-B42W-4N1Y", 60 bits
canonicalKey(ds, bits)   → String    any multiple of 5 from 20 to 255
keyForProtocol(p, bits)  → String    for a protocol already in hand
protocol(ds) / fromProtocol(p)       protocol of any symbol, and back
isCanonical(ds)          → boolean

Canonicalization is O(n²) in the size of the symbol, measured at about 11 µs per symbol over a mixed sample of sizes 4 to 24. That is cheap enough to call anywhere — per thumbnail, per redraw, in a sweep over millions.

Alongside it, GavrogInvariant is a port of DelaneySymbol.invariant() from Gavrog. It computes no identifiers of ours; passing -g appends it as a sixth column, for anyone who wants to join a catalog against Gavrog's own identifier for the same tiling. It is not carried in the published catalogs — it would add about half again to their size, to serve a handful of readers who can regenerate it in a minute. The two canonicalizations pick different representatives but induce exactly the same partition into isomorphism classes, checked over 30,759 symbols.

tegula.db.CatalogNumbering

java -Xmx8g -cp target/classes:'target/dependency/*' \
     tegula.db.CatalogNumbering -i tilings/tilings-1-19.tdb \
                                -o catalog/tilings-1-19.catalog.tsv.gz

Reads a .tdb, canonicalizes in parallel, sorts, numbers, and writes number, key, size, canonical_symbol, source_id. It reports isomorphic duplicates and hash collisions on every run. -k sets the key width, -m restricts by size, and -u adds indexed canonical_key and catalog_number columns to the database in place. Throughput is about 80,000 symbols per second on sixteen cores; all five databases rebuild in about four minutes.

Once a database carries the canonical_key column, Tegula's existing search box can already filter on it — the select expression is passed through to SQL unchanged.

Names in files

A Delaney symbol ends at its closing >. Anything after that on the line is read as a comment, optionally introduced by a #, and is available as getComment() / setComment(). It is written back out on save, so a name given to a tiling survives a round trip through a .tgs file:

<1000.0:1:1,1,1:3,6> # Alhambra star

The comment sits outside the D-symbol grammar, so the symbol itself is untouched — which is why it does not disturb the identity: it takes no part in comparison, canonicalization or the key, and canonical forms never carry one. That is deliberate. Keys and descriptive names are derived and must never be stored; only a nickname, which cannot be computed, belongs in a file.

Reading a collection now keeps only lines that hold a symbol. Blank lines, whole-line comments and stray text were previously parsed into empty symbols and drawn as blank tilings.

9 Decisions still open

  • 01 What is the universe of the published catalog?
    All 3-dimensional Delaney–Dress symbols of size ≤ N, unfiltered, is the recommendation. It has to be settled before any number is published, because it is the one thing that cannot be changed afterwards.
  • 02 One catalog or several?
    Splitting by geometry, as the current files do, means a tiling has several catalog numbers. One combined catalog with geometry as a queryable column avoids that. Keys are unaffected either way.
  • 03 Should duals be cross-linked?
    Storing the dual's key next to each entry is nearly free and makes duality navigable. Duals should not be folded into a single key — they are different tilings.
  • 04 Which cross-references should a published catalog carry?
    Gavrog's invariant can be generated on demand with -g, which is the right default for something only a few readers want. EPINET numbers its own D-symbol-defined hyperbolic tilings, as QC164 and the like, and that corpus overlaps ours directly, so matching against it is the more valuable link. Both are worth settling when the published list is settled, not before.
  • 05 Where does the resolver live?
    A static site generated from the catalog is enough — one page per key, with a rendered picture, the invariants, and the nickname if there is one.
